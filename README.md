# InternCheck MAX

> Рабочее название: чат-бот в MAX для самопроверки перед откликом на стажировку.

## Реализованная проверка ввода

Рабочая точка входа — `app/main.py`: последовательный polling MAX, личные диалоги и сессии в памяти. Проверки текста находятся в `app/parsing.py`, подбор вопросов и оценивание — в существующих `app/services/`. Структура JSON-данных сохранена. Разделы ниже также описывают планы проекта; наличие функции в плане не означает, что она уже реализована.

| Ситуация | Поведение бота |
| --- | --- |
| Пустой текст, пробелы, невидимые символы | Просит прислать текст; прогресс сохраняется |
| Фото, файл, голосовое сообщение без текста | Объясняет, что нужен текст; вложения не распознаёт |
| Более 8000 символов, управляющие символы, некорректный тип данных | Отклоняет ввод до анализа |
| Только ссылка или краткая подпись к ней | Просит скопировать требования; ссылки не загружает |
| Короткое или бессодержательное описание | Требует минимум 30 символов, четыре слова и 15 букв в тексте вне ссылок |
| Не найден Python, явно указано другое направление, нет подходящего теста | Объясняет ограничение и не начинает тест |
| Подходящее описание | Подбирает готовые вопросы по явно найденным навыкам; ждёт «да» |
| Несколько вариантов, неизвестная буква, кириллическая «а», число вне диапазона | Не засчитывает ответ; повторяет правила и текущий вопрос |
| Один допустимый вариант | Принимает латинскую букву без учёта регистра либо номер варианта; пробелы по краям допустимы |
| Новое описание во время теста | Предлагает сначала отменить текущий тест |
| Ответ после завершения | Предлагает результат, повторное прохождение или новое описание |
| Неизвестная команда или аргументы к команде | Показывает помощь без изменения ответов |
| Повтор того же события MAX | Не применяет ввод повторно, пока событие есть в кэше |
| Ответ отправлен до выдачи текущего вопроса | Отклоняет его, если доступны серверные метки времени |
| Ошибка расчёта или обработки | Сохраняет предыдущий прогресс; технические подробности пользователю не отправляет |

Команды: `/start` и `/continue` показывают текущий шаг, `/help` — помощь, `/result` — завершённый результат, `/cancel` — отмена. `/restart` очищает ответы только после подтверждения «да»; «нет» возвращает прежний этап. Для теста нужны Python и хотя бы одна дополнительная тема: SQL, Git или HTTP/REST. Упоминания GitHub, FastAPI и PostgreSQL сами по себе не добавляют Git, REST и SQL.

Перед выдачей проверяется структура банка вопросов. Неполные, повторяющиеся ответы и неизвестные варианты не допускаются к оцениванию. Правильность вычисляется по ключам вопросов, а пороги проверяются до округления процентов.

Ответы длиннее 4000 символов делятся на сообщения. При временном сбое отправки бот повторяет доставку сохранённого ответа с неотправленной части; уже полученная пачка обновлений остаётся в памяти. HTTP 403/404 при отправке пропускает недоступный диалог. Другие ошибки отправки требуют успешного повтора или устранения причины, например неверного токена. Ограничения доставки сверены с [методом отправки MAX](https://dev.max.ru/docs-api/methods/POST/messages) и [получением обновлений](https://dev.max.ru/docs-api/methods/GET/updates).

Ограничения: перезапуск процесса очищает сессии и кэш последних 2000 доставленных событий. Несколько процессов не разделяют состояние. При сетевом тайм-ауте после фактической доставки ответ бота может продублироваться, но ввод повторно не применяется в текущем процессе. Обычная новая буква без привязки к вопросу считается ответом на текущий вопрос; одинаковый текст с разными ID сообщений не является дублем события. Распознавание навыков и направления основано на словарях и простых правилах: произвольный текст не проверяется на достоверность или полный смысл. Групповые сообщения и callback-события пока не обрабатываются.

### Проверка изменений

Из корня репозитория в отдельном Python-окружении:

```powershell
python -m pip install -r requirements.txt pytest==8.3.5
python -m pytest -q -p no:cacheprovider
```

Сценарии ввода, переходы диалога, повторы событий и сетевые сбои покрыты в `tests/test_input_validation.py` и `tests/test_message_handling.py`. HTTP в этих тестах подменён; токен и реальная отправка сообщений не нужны. Проверка в живом диалоге MAX выполняется отдельно.

## Кратко о проекте

InternCheck MAX помогает пользователю пройти путь от интереса к конкретной стажировке до понятного следующего шага. Пользователь присылает описание стажировки, бот выделяет ключевые требования, предлагает короткий тест по нужным навыкам, оценивает ответы и либо рекомендует откликнуться, либо показывает конкретные зоны роста с объяснениями и упражнениями.

Главная идея MVP: **"хочу на эту стажировку -> проверил себя -> понял следующий шаг"**.

Для первой версии поддерживается одно направление стажировок, например Backend/Python, и заранее подготовленный качественный банк вопросов по основным темам.

## Проблема

Начинающему специалисту сложно понять, насколько он готов к конкретной стажировке. В описаниях вакансий много требований, а самостоятельная оценка обычно сводится к субъективному "кажется, знаю". Из-за этого пользователь либо не откликается на подходящую позицию, либо откликается, не понимая, какие темы нужно подтянуть.

## Решение

Бот превращает описание стажировки в короткую персональную проверку:

1. Принимает текст стажировки.
2. Выделяет навыки и темы из поддерживаемого набора.
3. Показывает, что именно будет проверено.
4. Формирует короткий тест из проверенного банка вопросов.
5. Проводит тест прямо в MAX.
6. Считает результат по каждой теме и общий результат.
7. Даёт один из двух понятных итогов: можно откликаться или сначала стоит подтянуть конкретные темы.
8. При ошибках выдаёт объяснение и 1-2 упражнения по каждой слабой теме.

## Что показываем жюри

Демонстрация строится вокруг одного законченного пользовательского сценария:

- пользователь отправляет описание стажировки;
- бот распознаёт, например, Python, SQL и Git;
- предлагает пройти проверку;
- пользователь отвечает на 6-10 вопросов;
- бот показывает общий результат и результат по темам;
- при хорошем результате предлагает откликнуться;
- при пробелах показывает конкретные зоны роста и упражнения.

Такой сценарий легко понять за несколько минут и в нём видна практическая польза продукта.

## Целевая аудитория

- студенты и выпускники;
- начинающие разработчики и аналитики;
- пользователи без коммерческого опыта;
- кандидаты, которым сложно оценить готовность к требованиям стажировки.

## Границы MVP

### Входит в MVP

- один тип стажировок, например Python/Backend;
- вставка пользователем текста описания стажировки;
- извлечение ключевых навыков из ограниченной таксономии;
- короткий тест из готового банка вопросов;
- ответы через кнопки и/или текст;
- автоматическая проверка;
- общий результат и результат по темам;
- объяснения ошибок;
- 1-2 упражнения на слабую тему;
- повторное прохождение теста;
- базовая история последнего прохождения.

### Не входит в MVP

- автоматический отклик на стажировку;
- отправка резюме работодателю;
- парсинг сайтов вакансий без участия пользователя;
- полноценная образовательная платформа;
- десятки направлений одновременно;
- генерация всех вопросов нейросетью в реальном времени;
- оценка soft skills, личности или "шансов получить оффер".

## Основной пользовательский сценарий

### 1. Старт

Пользователь запускает бота и видит короткое объяснение:

> Пришли описание стажировки. Я выделю ключевые требования и проверю знания по ним коротким тестом.

### 2. Получение стажировки

Пользователь отправляет текст вакансии или описание требований.

Бот валидирует сообщение: достаточно ли текста и удалось ли найти хотя бы один поддерживаемый навык.

### 3. Анализ требований

Бот преобразует свободный текст в нормализованный список навыков, например:

```json
{
  "direction": "python_backend",
  "skills": [
    {"name": "python", "weight": 0.4},
    {"name": "sql", "weight": 0.35},
    {"name": "git", "weight": 0.25}
  ]
}
```

Пользователь получает понятный ответ:

> В стажировке важны Python, SQL и Git. Проверка займёт около 5 минут.

### 4. Формирование теста

Для MVP вопросы выбираются из заранее подготовленного банка. Генерация теста учитывает найденные навыки и старается покрыть каждый из них.

Пример для 8 вопросов:

- Python - 3 вопроса;
- SQL - 3 вопроса;
- Git - 2 вопроса.

### 5. Прохождение

Бот отправляет вопросы по одному. Для вариантов ответа используются inline-кнопки. После ответа пользователь сразу переходит к следующему вопросу.

Для MVP лучше не показывать правильный ответ после каждого вопроса: итоговая обратная связь будет компактнее, а пользователь не сможет использовать предыдущие объяснения как подсказку к следующему вопросу.

### 6. Оценка

После последнего вопроса бот считает:

- общий процент правильных ответов;
- результат по каждому навыку;
- список тем, где были ошибки.

Пример правил MVP:

- 75-100% и нет критически слабой темы -> положительный результат;
- ниже 75% или хотя бы одна ключевая тема ниже 50% -> показать зоны роста.

Порог вынесен в конфигурацию и может меняться без переписывания логики.

### 7. Результат

Положительный вариант:

> Ты справился с проверенными темами. По этой проверке базовых знаний достаточно, чтобы переходить к отклику. Удачи!

Вариант с пробелами:

> По части тем пока есть сложности. Больше всего ошибок в JOIN и работе со словарями Python. Ниже - что стоит повторить и несколько упражнений.

Важно: бот не обещает получение стажировки и не делает вывод о найме. Он оценивает только темы, которые реально проверял.

## Логика продукта

### Почему банк вопросов, а не полностью генеративный тест

Для демо и первой версии критично, чтобы вопросы были корректными, одинаково оценивались и не менялись непредсказуемо. Поэтому рекомендуется разделить систему:

- LLM/анализатор - понимает текст стажировки, нормализует требования и может объяснять ошибки;
- Test Engine - выбирает вопросы из проверенного банка;
- Scoring Engine - детерминированно считает результат;
- Recommendation Engine - формирует следующий шаг по правилам.

Это снижает риск галлюцинаций и делает результат воспроизводимым.

## Поддерживаемая таксономия навыков

Для направления `python_backend` можно начать с:

| Навык | Темы MVP |
|---|---|
| Python | типы данных, условия, циклы, функции, коллекции, исключения |
| SQL | SELECT, WHERE, ORDER BY, GROUP BY, JOIN |
| Git | commit, branch, merge, pull/push, базовое понимание конфликтов |
| HTTP | методы GET/POST, статус-коды, запрос/ответ |
| Algorithms | простая оценка сложности, списки, словари, поиск |

На хакатоне не обязательно поддерживать всё. Достаточно 2-3 навыков, но с качественными вопросами и хорошей обратной связью.

## Формат банка вопросов

Рекомендуемый формат JSON/YAML:

```json
{
  "id": "sql_join_001",
  "direction": "python_backend",
  "skill": "sql",
  "topic": "join",
  "difficulty": "basic",
  "type": "single_choice",
  "question": "Какой JOIN оставит все строки из левой таблицы?",
  "options": ["INNER JOIN", "LEFT JOIN", "RIGHT JOIN", "CROSS JOIN"],
  "correct_option": 1,
  "explanation": "LEFT JOIN сохраняет все строки из левой таблицы и добавляет совпадения из правой.",
  "practice": [
    "Напиши запрос, который выводит всех пользователей и их заказы, включая пользователей без заказов.",
    "Сравни результат INNER JOIN и LEFT JOIN на двух небольших таблицах."
  ]
}
```

## Архитектура MVP

```text
MAX User
   |
   v
MAX Bot API
   |
   v
Webhook / Long Polling (dev)
   |
   v
Bot Application
   |-- Scenario / State Manager
   |-- Internship Analyzer
   |-- Test Engine
   |-- Scoring Engine
   |-- Feedback Engine
   |
   +--> Question Bank (JSON/YAML or DB)
   +--> Database (users, sessions, answers)
   +--> LLM provider (optional, for requirement extraction/explanations)
```

### Компоненты

**MAX adapter** - получает события, отправляет сообщения, обрабатывает callback-кнопки.

**Scenario/State Manager** - хранит текущий шаг пользователя: ожидание стажировки, подтверждение теста, номер вопроса, завершение.

**Internship Analyzer** - извлекает из текста только поддерживаемые навыки и приводит их к внутренним идентификаторам.

**Test Engine** - собирает тест из банка, не повторяет вопросы в рамках одной сессии.

**Scoring Engine** - проверяет ответы и считает общий/тематический балл.

**Feedback Engine** - превращает результаты в понятную обратную связь и подбирает упражнения.

**Storage** - сохраняет сессии, ответы и результаты.

## Рекомендуемый стек

Стек можно заменить без изменения продуктовой логики. Для быстрого MVP:

- Python 3.11+;
- FastAPI - webhook endpoint и служебное API;
- httpx - запросы к MAX API и LLM;
- Pydantic - модели данных и валидация;
- PostgreSQL - production/командная разработка;
- SQLite - допустимо для локального демо;
- SQLAlchemy + Alembic - работа с БД и миграции;
- pytest - тесты;
- Docker / Docker Compose - воспроизводимый запуск;
- LLM API - опционально для извлечения требований и генерации объяснений.

MAX публикует OpenAPI-спецификацию, поэтому при желании можно сгенерировать клиент для Python. В официальной документации также есть готовые библиотеки/примеры для JavaScript и Go.

## Интеграция с MAX

Актуальная базовая точка API:

```text
https://platform-api2.max.ru/
```

Токен передаётся в заголовке:

```text
Authorization: <access_token>
```

Для production рекомендуется Webhook. Long Polling можно использовать для локальной разработки и тестов, но документация MAX не рекомендует его как production-механизм.

Для webhook-подписки следует использовать HTTPS. Дополнительно рекомендуется задать `secret` и проверять заголовок `X-Max-Bot-Api-Secret` на своей стороне.

Для тестов с кнопками удобно подписаться минимум на события сообщений и callback-действий пользователя.

Важно: правила и API MAX меняются. Перед финальной публикацией сверяйтесь с официальной документацией.

## Состояния диалога

Минимальная конечная машина состояний:

```text
IDLE
  -> WAITING_INTERNSHIP
  -> INTERNSHIP_ANALYZED
  -> TEST_IN_PROGRESS
  -> RESULT
  -> REVIEW_GAPS (optional)
  -> IDLE / RETAKE
```

В каждый момент времени сервер должен понимать, какое действие ожидается от пользователя. Не полагайтесь только на текст последнего сообщения - сохраняйте состояние сессии.

## Правила анализа стажировки

Чтобы MVP был устойчивым, анализатор должен возвращать данные в строгом формате и работать только с разрешённой таксономией.

Пример системного правила для LLM:

```text
Извлеки только технические навыки, присутствующие в ALLOWED_SKILLS.
Не добавляй навыки, которых нет в тексте.
Верни только JSON по заданной схеме.
Если поддерживаемых навыков нет, верни пустой массив.
```

После ответа LLM данные обязательно валидируются на сервере через Pydantic/JSON Schema.

Если LLM недоступна, можно использовать запасной rule-based анализ по ключевым словам. Для хакатона такой fallback полезен: основной сценарий не ломается из-за внешнего API.

## Алгоритм формирования теста

1. Получить найденные навыки.
2. Отфильтровать неподдерживаемые.
3. Определить количество вопросов на навык.
4. Выбрать базовые вопросы из банка.
5. Перемешать порядок вопросов/вариантов, если это не мешает корректности.
6. Сохранить список `question_id` в попытке.
7. Отправлять по одному вопросу.
8. После каждого ответа фиксировать результат.
9. После последнего ответа посчитать статистику.

## Алгоритм оценки

```python
score_total = correct_answers / total_questions
skill_score = correct_by_skill / questions_by_skill

passed = (
    score_total >= PASS_SCORE
    and min(critical_skill_scores) >= CRITICAL_SKILL_SCORE
)
```

Для очень коротких блоков (1 вопрос на тему) не стоит делать сильные выводы по проценту. Лучше формулировать: "в этом вопросе по JOIN была ошибка", а не "ты плохо знаешь SQL".

## Формат обратной связи

Рекомендуется держать результат коротким и практичным:

```text
Результат: 6/8 (75%)

Python: 3/3
SQL: 2/3
Git: 1/2

Зона роста: SQL JOIN
Коротко: повтори разницу INNER JOIN и LEFT JOIN.
Практика:
1. Выведи всех пользователей и их заказы, включая пользователей без заказов.
2. Сравни INNER JOIN и LEFT JOIN на двух таблицах.

Следующий шаг: повтори тему и пройди тест ещё раз.
```

## Обработка ошибок

Бот должен корректно обрабатывать:

- пустое или слишком короткое описание;
- стажировку вне поддерживаемого направления;
- отсутствие распознанных навыков;
- повторное нажатие callback-кнопки;
- потерю/истечение сессии;
- ошибку MAX API;
- таймаут LLM;
- некорректный JSON от LLM;
- недоступность БД;
- повторную доставку webhook-события.

Для webhook-обработчика желательно обеспечить идемпотентность: одно и то же событие не должно дважды записывать ответ или дважды переключать вопрос.

## Безопасность и приватность

- не логировать `MAX_BOT_TOKEN`, webhook secret и LLM API key;
- секреты хранить только в переменных окружения/секрет-хранилище;
- webhook принимать только по HTTPS;
- при использовании webhook secret проверять `X-Max-Bot-Api-Secret`;
- ограничить размер входного текста;
- экранировать/валидировать пользовательские данные перед записью и выводом;
- не отправлять в LLM лишние персональные данные;
- предусмотреть удаление истории пользователя;
- не давать ложных гарантий трудоустройства.

## Тестирование

### Unit tests

Проверить отдельно:

- нормализацию навыков;
- выбор вопросов;
- отсутствие дублей в тесте;
- подсчёт общего балла;
- балл по темам;
- пороги `PASS_SCORE` и `CRITICAL_SKILL_SCORE`;
- выбор зон роста;
- обработку некорректного ответа анализатора.

### Integration tests

Проверить цепочки:

1. стажировка -> навыки -> старт теста;
2. полный тест -> положительный результат;
3. полный тест -> зоны роста;
4. LLM timeout -> fallback;
5. повторный callback -> ответ не дублируется;
6. восстановление сессии после перезапуска приложения.

### Demo smoke test

Перед защитой вручную пройти два заранее подготовленных сценария:

- успешный пользователь;
- пользователь с ошибками в одной теме.

## Демонстрационный сценарий для жюри

### Сценарий A: готов к отклику

1. Отправить подготовленное описание Python-стажировки.
2. Бот показывает: Python + SQL + Git.
3. Нажать "Начать тест".
4. Ответить правильно на большинство вопросов.
5. Получить результат выше порога.
6. Бот сообщает, что по проверенным темам базовая подготовка достаточная и можно переходить к отклику.

### Сценарий B: есть пробел

1. Отправить ту же стажировку.
2. В тесте специально ошибиться в SQL JOIN.
3. Бот показывает SQL/JOIN как зону роста.
4. Бот даёт короткое объяснение и два упражнения.
5. Показать кнопку "Пройти ещё раз".

Так жюри видит не просто чат, а полный продуктовый цикл и персональный следующий шаг.

## Критерии готовности MVP

MVP можно считать готовым к демонстрации, если:

- пользователь может пройти основной сценарий без ручного вмешательства разработчика;
- минимум одно направление стажировок распознаётся стабильно;
- тест содержит не менее 15-25 проверенных вопросов в банке;
- результат считается детерминированно;
- ошибки по темам отображаются корректно;
- есть минимум по 1-2 упражнения на основные темы;
- повторное прохождение работает;
- бот не ломается при невалидном вводе;
- секреты не находятся в репозитории;
- есть автоматические тесты на scoring и test engine.

## Метрики успеха

Для хакатона достаточно продуктовых метрик, которые можно собирать после MVP:

- доля пользователей, которые после анализа начинают тест;
- доля пользователей, которые заканчивают тест;
- среднее время прохождения;
- доля пользователей, которые открывают рекомендации по слабым темам;
- доля повторных прохождений;
- распределение ошибок по темам.

Не стоит использовать "получил ли пользователь стажировку" как основную MVP-метрику: на неё влияет слишком много факторов вне продукта.

## Roadmap

### Этап 1 - Hackathon MVP

- одно направление;
- ручная вставка описания;
- 2-4 поддерживаемых навыка;
- фиксированный банк вопросов;
- deterministic scoring;
- зоны роста и упражнения;
- MAX Bot API;
- базовая БД.

### Этап 2 - Расширение контента

- Data Analytics, QA, Frontend, Java и другие направления;
- уровни сложности;
- больше типов вопросов;
- адаптивный тест в зависимости от предыдущих ответов.

### Этап 3 - Персонализация

- история попыток;
- прогресс по навыкам;
- персональные повторения;
- рекомендации материалов;
- сравнение результата до и после подготовки.

### Этап 4 - Работа с вакансиями

- загрузка ссылок/файлов при наличии легального и технического доступа;
- сохранение выбранных стажировок;
- сравнение требований нескольких стажировок;
- профиль навыков пользователя.

## Возможное распределение задач в команде

- Backend: MAX API, webhook, FSM, БД, scoring;
- AI/ML: анализ требований, structured output, fallback;
- Content: вопросы, объяснения, упражнения;
- Product/UX: сценарии, тексты, demo-flow;
- DevOps: деплой, HTTPS, секреты, мониторинг.

При маленькой команде Backend + AI можно объединить, а контент подготовить заранее совместно.

## Риски MVP и как их снизить

| Риск | Решение |
|---|---|
| LLM неправильно выделяет требования | Закрытая таксономия + строгая JSON-схема + fallback по ключевым словам |
| Генерируется плохой вопрос | В MVP использовать только проверенный банк |
| Демо зависит от внешнего API | Кэш/готовый fallback-анализ для демонстрационной вакансии |
| Пользователь бросает длинный тест | 6-10 вопросов, прогресс `3/8` |
| Оценка звучит слишком категорично | Говорить только о проверенных темах, не прогнозировать найм |
| Ошибка/повтор webhook | Идемпотентная обработка event/update ID |
| Не хватает времени на много направлений | Одно направление, но полноценный end-to-end сценарий |

## Принципы UX

- один экран/сообщение - одно действие;
- короткие сообщения вместо длинных лекций;
- прогресс во время теста: `Вопрос 4 из 8`;
- минимум свободного ввода во время теста;
- кнопки "Начать тест", "Следующий шаг", "Разобрать ошибки", "Пройти ещё раз";
- результат сначала, объяснения ниже;
- не перегружать пользователя техническими процентами, если выборка мала.

## Definition of Done

Функция считается готовой, если она:

1. работает в основном сценарии в MAX;
2. имеет обработку ошибок;
3. покрыта хотя бы базовым unit/integration тестом;
4. не требует ручного исправления данных;
5. не раскрывает секреты;
6. имеет понятный текст для пользователя;
7. воспроизводится на чистом окружении по инструкции запуска.

## Итог

InternCheck MAX - это не "ещё один бот с вопросами", а короткий decision-support сценарий перед откликом на стажировку. Пользователь приносит конкретную стажировку, получает проверку именно по её требованиям и сразу понимает следующий шаг: откликаться или сначала закрыть конкретный пробел.

Для хакатона сильнее всего выглядит не количество функций, а завершённость этого одного пути и качество тестов/обратной связи.
